# Community fact vote counter rollout

Apply `20261116_safe_fact_votes.sql` before deploying the matching web code. The migration is intended for a database where the earlier worktree version of this migration has not been applied. Inspect the live functions, triggers, grants, RLS policies and migration history immediately before rollout. Apply the migration transactionally. Do not run a historical counter backfill as part of this change.

New fact inserts still accept legacy payloads, but ignore supplied corroboration and dispute totals. A nonblank contributor token gives an initial corroboration and a matching vote in the same transaction; failure to create the vote rolls back the fact. The internal creator-vote insert runs as the function owner and bypasses the vote table's RLS; the original fact insert remains subject to its own RLS. Legacy clients' subsequent duplicate vote insert may fail, as their code already tolerates, and their counter RPC remains a no-op.

The baseline vote policy uses a self-comparison, imposing a global hourly cap. This migration replaces it with a correlated check of the incoming token against recent votes: ordinary anonymous inserts and RPC votes are allowed while that token has fewer than 20 visible votes in the past hour. The check depends on the existing `read_votes` SELECT policy continuing to expose all votes to anon. The fact-insert policy is unchanged: its self-comparison still imposes a nominal global limit of fewer than 10 facts in the preceding hour. The internal creator vote bypasses the vote policy, but it is included in later checks.

This is a best-effort check, not a strict rate limiter: simultaneous or multi-row inserts can see the same prior count, and clients can supply `created_at` for direct vote inserts. Tokens can also be freely changed. Do not present this as abuse prevention or a guaranteed 20-vote ceiling.

Counts on existing facts are not repaired or verified. In particular, an old fact can have a creator count but no creator vote; a later successful vote by that token will be counted, potentially leaving a historical overcount. Conversely, pre-existing discrepancies remain. A separate evidence-based reconciliation would be required.

Tokens are anonymous client-supplied identifiers, not authenticated identities or secrets. Anyone able to learn or guess one can cast a vote with it, including claiming a creator token on a new fact; the uniqueness constraint then occupies that token for that fact. New tokens can also be generated freely. This change prevents arbitrary supplied totals and avoids exempting later votes just because a token matches the contributor; it does not prevent impersonation, ballot stuffing, fraudulent submissions or misuse of other fact fields.

## Coordinated application rollback

This is an app rollback with a retained database compatibility bridge, not a full schema revert. Removing the triggers or restoring the old increment RPC while old or cached new clients can write would lose or double-count votes, break the new app, or restore arbitrary counter increments. There is no safe automatic full return to the old schema. Do not delete vote rows, reset counters, or replay an old database snapshot over live data; all votes accumulated before and after migration must remain.

1. Before rollout, record the served app revision, migration revision, actual live function/trigger/policy definitions, permissions and migration history, and ensure a restorable backup. This is a future operator action, not performed by this change. Apply the migration first; deploying the new app first leaves its vote RPC unavailable and its fact submissions without creator-vote records.
2. For an app rollback, first inspect the current schema and compare it with the migrated definitions and granted roles. Stop and investigate any drift, inactive triggers, missing RPC, changed `read_votes` policy, or failed checks. Retain the full vote and fact tables and their current totals. Confirm the previous app revision and routing plan, including old tabs and in-flight requests.
3. Apply `supabase/rollbacks/20261116_fact_votes_app_rollback_bridge.sql` as one transaction. It locks both tables briefly, checks required bridge pieces, keeps the old increment RPC harmless, and reinstates the per-token insert policy. It does not remove the triggers or new RPC and does not alter vote rows or counters. Its checks are not a substitute for comparing actual function bodies, owners, privileges, and all effective policies with the reviewed deployment. Abort on any mismatch; do not execute a partially matching script.
4. Roll back the app to the verified prior revision. The bridge supports the legacy direct-insert-plus-increment sequence and the new RPC while cached clients drain. A legacy creator's duplicate follow-up insert can fail harmlessly; older UI may still optimistically display success if a vote fails. Verify served revision, successful old and new client paths, duplicate handling, and current vote/counter evidence. Do not issue test votes against production without separate authorization.
5. Keep the bridge until a separately designed and tested removal can account for every client and in-flight write. A full return to the original SQL would restore its known unsafe counter RPC and global vote policy; it is not provided as a safe rollback.
